# Measurement discipline — the incidents behind the rule

**Load this when:** two instruments disagree, or a gate refuses for a reason naming another branch's work, or you are about to act on a number you did not derive in this turn. **Do not load it on a clean pass.**

The always-rule lives in `../SKILL.md` invariant 4 and is enough on a good day: *measure immediately before the action the measurement authorises, and record the instant beside the value.* What follows is the evidence for it — six distinct bugs, each of which cost a real run — plus the gate-reading discipline that grew out of them.

## The six ways a reading goes stale

| What you measured | How it goes stale |
|---|---|
| A gate's exit code | A peer commits; an ancestry gate flips back to red, silently → *see `orchestration-deadlocks.md`* |
| Branch topology | A late push moves a head; the branch you named no longer carries the work → *step-06* |
| "These branches are independent" | Anything merging anywhere can falsify it — it decays fastest of all → *step-06* |
| A derived count | Remote-only migrations went 9 → 16 in hours |
| A file you plan to edit | Another session already rewrote it, or already fixed the thing you were going to fix |
| A fork's report | It was true when written and the fork has since pushed → *step-05* |

## Reading a gate

- **Read the gate's resolution predicate; never trust its help text.** A gate that prints a suggested fix is stating an intention, not a proof — and the two drift. Observed: a collision gate whose failure message suggested copying files from another ref, while the condition it actually tested was branch *ancestry*. Following the printed advice left it exactly as red, with no hint why, and the suggested command wrote the index as a bonus. Open the gate script, find the line that decides pass/fail, and satisfy **that**.
- **A red gate can be a correct *description* rather than a verdict on your code.** Same measurement, different reading. Observed on a collapsed topology: a fork could not push because the collision gate found a sibling's tip was not its ancestor. Both escapes were worse than the block — the bypass is forbidden, and merging the sibling would have produced a **second** branch claiming to carry the whole run, the very defect the orchestrator had prevented an hour earlier from the opposite direction. The gate was right, and the right response was *this branch no longer needs to exist separately*, not *fix this branch*. Before fixing, ask what the gate is actually asserting — sometimes it is describing a topology, not accusing a diff.
- **A correct number that answers a different question is the most recurrent failure there is.** A fork reported seven migrations: true of its own spec, false as an answer to "how many did this run apply" — the real figure was nine. Nothing was dishonest and nothing was wrong; the value simply answered a question the reader was not asking. **When you quote a number, say what it counts.**
- **A gate that did not finish did not decide.** Before believing a rejection, check that it *ran to completion*. A killed task rejected nothing — and the usual killer is not its own timeout but the **hook runner cancelling its siblings the moment one of them fails**, which is how a perfectly healthy gate ends up in the output looking guilty.
- **A symptom with no printed reason attracts the cause you are already holding.** This is the one that actually bites, and it is a diagnostic bias, not a property of gates. A cancelled task prints no reason of its own, so the reader supplies one — and supplies whatever they were already thinking about. Observed, as a genuine misdiagnosis in a live run: an orchestrator holding a real deploy-set collision read two cancelled gate tasks as that collision inflating a type-check. They were unrelated; the actual failure was a lint error in a sibling task of the same glob, and the collision explained none of it. **Before attributing a reasonless symptom to a cause you already have in hand, go find that symptom's own reason** — read the sibling tasks, re-run the gate alone. Resist the tidiness of one cause explaining everything; it is exactly as wrong as missing a shared cause, and much more satisfying, which is what makes it dangerous.
- **A gate invoked with no arguments may exit 0 without checking anything.** Sharpest instance of the rule below, and worth its own line because the output is indistinguishable from a pass: a migration gate run bare exited 0 with files staged; given the paths explicitly, it rejected them. The same gate also silently skipped any file that was not staged. Two independent ways to collect a green that was never a check — from one script.
- **Reproduce a gate exactly the way the hook invokes it — both directions lie otherwise.** Run standalone, a gate can print a confident refusal it would never have produced in the real path (one only sees files once they are *staged*, so invoked directly it rejects with total conviction while never actually firing — perfect material for talking yourself into `--no-verify` over a gate that was never going to block). And the reverse: a check the hook runs with a relaxing flag can look alarming when you run it raw, while structurally being unable to block anything (a suite the gate runs with type-checking disabled goes red on pre-existing type errors that no push has ever been stopped by). Neither the scary red nor the confident red means what it appears to until you have matched the invocation.

- **For a shared target, the mitigation is not a lock — it is re-reading at the moment of writing** (*Every measurement is a reading*, applied to files). The default branch is the one surface no worktree isolates, and the contention there is usually not with your own forks — they never touch it — but with **another session on the machine**. Two things sufficed in a five-fork run: run the docs phase **strictly last**, after every fork has closed, so it never races your own work; and **re-read every target file as you write it** rather than trusting the Step 2 survey. That re-read found **three of four documents already corrected** by the other session — the pending item was itself the stale thing — and caught an item that would have deleted 27 of a view's 72 lines.
